# ProxyPolicyGenerator — GrantPermission ceiling + PERMISSIONS.LIST tool

*Implements `docs/SOW-GrantPermission-PolicyTool.md`.*

`org.apache.river.tool.ProxyPolicyGenerator` removes two hand-authoring chores
from the policy writer by deriving them from an audited run:

1. the **minimal `GrantPermission` ceiling** that bounds what may be dynamically
   granted to a proxy, and
2. the per-codebase **`META-INF/PERMISSIONS.LIST`** declared-needs manifest.

It is a post-processor over the least-privilege policy produced by the
`polpAudit` workflow (`SecurityPolicyWriter` → `PolicyCondenser`). It lives in
the `policy-condenser` tool module, package `org.apache.river.tool`, alongside
`SecurityPolicyWriter`, `PolicyCondenser` and `PolicyUpdatePostProcessor`.

## Where it sits in the meet

The effective grant to a proxy is the conjunction of three terms. `polpAudit`
already produces the **scoped least-privilege grant blocks** (the floor). This
tool derives the other two least-automated terms:

| Term | Authored by | Produced here |
|------|-------------|---------------|
| Scoped grant block (floor) | `polpAudit` (`SecurityPolicyWriter`) | — |
| `GrantPermission` ceiling (delegation bound) | hand, today | **yes** (`<policy>.grantperm`) |
| `PERMISSIONS.LIST` (declared-needs cap) | hand, today | **yes** (`<artefact>/META-INF/PERMISSIONS.LIST`) |

## Usage

```
java -cp policy-condenser.jar:jgdms-platform.jar \
     org.apache.river.tool.ProxyPolicyGenerator \
     [--out <dir>] [--proxy-regex <regex>] [--strict] [--clean] \
     [--fail-on-held] [--fail-on-empty] [--diff-against <dir>] \
     [--properties <file>] <policy-file> [<policy-file> ...]
```

| Flag | Meaning |
|------|---------|
| `--strict` | Classification only: a grant needs a proxy-shape permission (`AccessPermission` etc.) to count as a proxy. It never refuses a run. |
| `--fail-on-held` | Refuse the run, writing nothing, if any entry would be written as `# HELD` (see below). Independent of `--strict`: it works on a policy whose proxies have no `AccessPermission`. |
| `--fail-on-empty` | Refuse the run if a proxy group is left with no live entry. Without it such a group gets no list and a `NO LIST WRITTEN` note. |
| `--clean` | Delete the lists already under `--out` that this tool wrote (they carry the `# Source policy:` header, or the old `# Generated by ProxyPolicyGenerator` line of lists from before provenance) instead of refusing a directory that holds lists from another policy, or from the same file name with other content. It also acts when the policy has no proxy grant. A list with neither marker is hand-written: it is never deleted, a run that would replace one is refused (with or without `--clean`), and one the run does not touch is kept with a `KEPT` note that is true. |
| `--diff-against <dir>` | Print, per artefact, the live entries added to and removed from the checked-in list of the same module; reads `<dir>` only. |

The CLI exits 0 on success, 1 if a policy was refused, 2 on a usage error.

For each `<policy-file>` it writes:

* `<policy-file>.grantperm` — a policy fragment with the synthesised
  `GrantPermission` ceiling grant blocks, and
* `<out>/<artefact>/META-INF/PERMISSIONS.LIST` per proxy codebase
  (default `<out>` is `<policy-file>.proxy-permissions`).

In the QA harness it runs automatically as step 3 of `PolicyUpdatePostProcessor`
after each `ant -Dpolicy.update=true policy-update` run (disable with
`-Dpolicy.update.generate.proxy=false`).

## Proxy identification

The **hard key** is the codebase / artefact naming convention. A grant block is
proxy-targeted when:

* it carries a `digest` scope clause (a content-addressed `DigestCodeSource`
  grant — the strongest signal), **or**
* its `codebase` matches the proxy-artefact regex. The default matches the
  `httpmd:` integrity-protected scheme and the JGDMS download/proxy artefact
  convention `*-dl.jar` / `*-dl-<version>.jar` (e.g. `mahalo-dl.jar`,
  `reggie-dl-3.1.1.jar`). Confirmed against the modules that ship a
  `PERMISSIONS.LIST` today — they are exactly the `*-dl` download modules.

Override the regex with `--proxy-regex` or
`-Dorg.apache.river.tool.ProxyPolicyGenerator.proxy.codebase.regex=…`.

The **permission-set shape** (`AccessPermission`, `AuthenticationPermission`,
`net.jini.jeri`/`net.jini.export`/`net.jini.io.context` permissions) is used
only as a corroborating confidence annotation in the output — never as the sole
key. With `--strict`, a corroborating proxy-shape permission is additionally
*required* before a codebase is treated as proxy-targeted.

## Guarantees

* **Round-trip.** `PERMISSIONS.LIST` entries are encoded with
  `AdvisoryPermissionParser.getEncoded(...)` (so they parse back via
  `AdvisoryPermissionParser.parse`); each ceiling is validated by constructing a
  `GrantPermission` from its target string and the emitted grant block parses
  back via `DefaultPolicyParser`. (Note: policy fragments use `//` comments;
  `PERMISSIONS.LIST` uses `#`/`//`.)
* **Minimality.** A ceiling lists exactly the proxy's exercised non-meta
  permissions — no broader.
* **Fail-closed.** A codebase that exercised no non-meta permission yields no
  manifest and no ceiling; meta-capabilities (`GrantPermission`,
  `UmbrellaGrantPermission`, `AllPermission`) are excluded from
  `PERMISSIONS.LIST` and the ceiling.
* **Property substitution.** `--properties <file>` (property-name = literal
  value) replaces literal paths/hosts with `${property}` placeholders in emitted
  targets, longest value first.

## What goes into a `PERMISSIONS.LIST`

A jar's own `META-INF/PERMISSIONS.LIST` is its *request* for permissions
(`PreferredClassLoader`). The generated list is therefore held to what a
reviewer can stand behind:

* **Gate permissions are dropped.** `LoadClassPermission` (both recorded
  names), `URLPermission` and `DownloadPermission` are written as
  `# DROPPED (reason): entry`: the proxy provider grants them after verifying the
  codebase, and a jar must not request its own admission. They stay in the
  `.grantperm` ceiling.
* **Host- and run-specific entries are held.** Absolute paths, `file:` URLs,
  `jdk.proxyN.$ProxyM` class names and unexpanded `${...}` placeholders (the
  loader does not expand them) are written as `# HELD (reason): entry`.
  `--fail-on-held` turns them into a refusal.
* **A list with no live entry is not written.** An empty list requests the same
  as no list, so promoting one would silently remove the reviewed entries of the
  list it replaces. The result carries `NO LIST WRITTEN: all N entries dropped or
  held for <artefact>` (stderr on the CLI); `--fail-on-empty` fails the run.
* **Provenance.** The header records `# Source policy:` (file name),
  `# Source policy SHA-256:`, the generator version and format, the date, and the
  grant digest. A list **this run replaces never refuses**, whatever policy or
  content it was made from, so a re-audit works by default. Only a list that
  survives the run unreplaced is checked: one from another policy, from the same
  name with different content (another host's audit), or with no provenance line
  is refused unless `--clean`. Two kinds of list without a `# Source policy:` line
  are told apart: one with the old `# Generated by ProxyPolicyGenerator (do not
  edit by hand).` line (the 14 committed lists carry it) was written by this tool,
  so a run replaces it with a `REPLACED pre-provenance list` note and `--clean`
  deletes one it does not replace with a `REMOVED` note; one with neither marker
  is hand-written and is never replaced or deleted, with or without `--clean`
  (a `--clean` run that would replace it is refused; move it away). The check also
  runs for a policy with no proxy grants, where it reports the lists left behind as
  `STALE` (and `--clean` deletes the tool-written ones). Host is not part of the
  key: the header has none.
* **One artefact name is one list.** If two codebases of a policy map to the same
  artefact name (for example `httpmd://${HOST}:9080/${reggie-dl.jar}` and
  `httpmd://${HOST}:${reggie-dl.jar}` in `defaultsecuretest.policy.old`, or names
  that differ only in case), the run is refused, naming both codebases, and writes
  nothing. They are never merged: a union would widen a list. Give the codebases
  distinct jar names or generate them from separate policies.
* **No control or format characters.** A newline in a digest, codebase, or
  permission type, name or actions would start a live line (for example
  `(java.security.AllPermission)`); a Unicode bidirectional override or other
  format character (category Cf, so zero-width and tag characters too) or U+2028/9
  would make a reviewer read something other than what is written. The run is
  refused. The same check covers `signedBy`, principal class and principal name,
  which reach the `.grantperm` ceiling.
* **Never delete what it did not write.** `<policy>.grantperm` is deleted (no
  proxy grant left) or overwritten only if it carries this tool's header comment;
  otherwise a run with proxy grants is refused and one without keeps it and says
  `KEPT`.
* **All or nothing.** Lists are written to a staging directory beside `--out`,
  every line is parsed back with `AdvisoryPermissionParser.parse` (the loader drops
  a jar's whole list silently on one bad line), and only then are they moved into
  place. A refusal leaves `--out` and the `.grantperm` exactly as they were. The
  final moves are not atomic as a group: an I/O error during them can leave some
  lists moved. (Promotion has the same known limit, below.)

`PolicyUpdatePostProcessor` logs the DROPPED, HELD, STALE and NO LIST WRITTEN notes
and every refusal at WARNING, and warns of any `<policy>.proxy-permissions`
directory under the qa tree that no processed policy regenerates. A re-audit
replaces the earlier lists of the same artefacts without any flag; a list the new
policy no longer produces is refused until `-Dpolicy.update.proxy.clean=true` is
given (or reported `STALE` when it came from the same policy and content).
`policy-update` does not set `--fail-on-held`: held entries are reported, and the
promotion step is where they are refused.

### Artefact names

The artefact directory is named from the last path segment of the codebase.
`${/}` is read as `/`, and a segment that names the jar by a property
(`${reggie-dl.jar}`, `${HOST}:${jsk-dl.jar}`) is unwrapped to the last
`${name.jar}` group, so `file:${jsk.home}${/}lib-dl${/}${phoenix-dl.jar}` is
`phoenix-dl`. Names that still cannot be guessed (for example `qa1-mahalo-dl`, a
wildcard codebase) stay `REFUSED` at promotion; `--artefact-map <file>` names the
module for them, one `sanitised-name = module-dir-name` per line (`#` comments
and blank lines allowed). The map is reviewed and checked in by a human; a name
mapped to a module that does not exist is refused, an unmapped name is refused.

## Promoting reviewed lists into the modules

Generated lists live under `<policy>.proxy-permissions/`. The `-dl` modules
carry the ones that ship, at `<module>/src/main/resources/META-INF/PERMISSIONS.LIST`.
Promotion is deliberately two steps, because the operator's process is: run the
audit (`polpAudit`), generate the policy, **audit that policy**, and simulate all
user operations so that the principal and digest grants are appropriate. A list
that comes out of this tool has been through the first half; whether it is the
right *request* for the jar is a review decision the tool must not make for you.

The list is a jar's own declared-needs cap, one term of the effective grant. So
promotion never writes outside the module roots and never widens what was
reviewed, and **the plan file is a record of what the human read, never an
instruction**: apply trusts nothing in it that the planner can re-derive.

1. **Plan** (changes nothing under the module roots):

   ```
   ProxyPolicyGenerator --out <x.policy.proxy-permissions> [--plan-file <file>] \
       [--artefact-map <file>] --promote-plan <module-root>[ <module-root>...]
   ant -Dpromote.out=<dir> policy-promote-plan          # qa/build.xml
   ```

   Each generated artefact (`mahalo-dl-4.0.0-SNAPSHOT`) is mapped to the `-dl`
   module of its name without the version (`mahalo-dl`, found under the module
   roots) or by the artefact map. Module discovery works on real paths: a module
   directory that is a symbolic link or junction refuses the whole plan, and a
   link that is not itself a module is not entered. The plan file (default
   `<out>/promote.plan`, refused under a module root) lists per artefact: the
   target path, `ADDED` and `REMOVED` entries against the checked-in list
   (compared as parsed), or `NEW FILE`, the **held and dropped counts**, the
   DROPPED and HELD notes, checked-in comments that the replacement will not carry
   over, the **source kind** and `REFUSED` with a reason where promotion is
   impossible (no such module, ambiguous module, no live entry, no provenance
   line, an unparseable line). It records the SHA-256 of the generated list and
   of the target, and the command prints `plan sha256: <sha>`.

   *Source kind* says what produced the policy the list came from, when the plan
   can tell: it finds the policy named in the list's header beside the generated
   lists, checks it is the file with the recorded SHA-256, and reports
   `hand-written or template policy` if it holds `${...}` or
   `polpAudit-generated policy` if a comment names polpAudit. A polpAudit policy
   carries no marker of its own, so most plans say `source kind: unknown (...)`
   and give the reason; it is never guessed.

2. **Review the plan** against the audit, then **apply** only what you approve.
   Apply takes the same `--out` and module roots (and artefact map) as the plan,
   and the SHA-256 the plan printed:

   ```
   ProxyPolicyGenerator --promote-apply <plan-file> --approve-plan-sha <sha> \
       --out <x.policy.proxy-permissions> [--artefact-map <file>] \
       --module-roots <module-root>[ <module-root>...] \
       --approve <artefact>[,<artefact>...] [--allow-removals] [--allow-held]
   ant -Dpromote.out=<dir> -Dpromote.plan.sha=<sha> -Dpromote.approve=a,b \
       [-Dpromote.allow.removals=true] [-Dpromote.allow.held=true] policy-promote-apply
   ```

   Only the named artefacts are written. Apply re-runs the planner in memory from
   the generated lists and the roots and, for every approved artefact, refuses
   unless the re-derived entry (target path, generated hash, target hash, added
   and removed entries, notes, status) is identical to the plan file's. It also
   requires the canonical target to be under a canonical module root and to end
   with `src/main/resources/META-INF/PERMISSIONS.LIST`. Every approved artefact is
   checked first and nothing is written if any is refused. Refused: a plan file
   whose SHA-256 is not the one given; an artefact the plan refused or does not
   contain; a plan older than the generated list or a generated list whose hash
   changed; a target that changed (or appeared) since the plan; a target outside
   the roots or not a `PERMISSIONS.LIST`; a list with no live entry or no
   provenance (re-derived, whatever the plan file says); an artefact with
   `REMOVED` entries unless `--allow-removals`; and an artefact with held entries
   unless `--allow-held`.

   The new content is staged in a directory under the plan file's directory
   (nothing is left inside `src/main/resources`), then moved into place, keeping
   the target's line-ending style (LF for a new file). If a move fails, the
   targets already moved are restored from backups kept in the staging directory
   and the error says so (if a restore fails too the backups are left and named).
   Each write is printed with its held and dropped counts.

3. **CI gate** (plan only; apply stays manual):

   ```
   ProxyPolicyGenerator --out <dir> [--artefact-map <file>] --promote-plan-check <module-root>...
   ant -Dpromote.out=<dir> policy-promote-check
   ```

   Writes no file. It prints the plan summary and the `ADDED` entries per artefact
   (an audit is a sample, so an addition is information) and exits 1 if any
   artefact has `REMOVED` entries (the checked-in jar requests more than the audit
   observed) or a list that does not parse. Artefacts the planner refuses for
   other reasons (no such module) do not fail the gate.

   The plan, the gate and apply apply the generator's own exclusions. A list under
   `--out` that holds `AllPermission`, `GrantPermission`, `UmbrellaGrantPermission`
   or any `LoadClassPermission`, `URLPermission` or `DownloadPermission` entry was
   edited (the generator never writes one): the plan marks it `REFUSED: the list
   was edited`, the gate exits 1 and apply refuses. The same holds for a control or
   format character on any line, which is re-checked at plan, gate and apply time;
   output (plan file, summary, gate report, error messages) shows such characters as
   a backslash-u escape, never raw. Two artefacts that resolve to one module target
   (a stale `mahalo-dl-4.0.1` beside `mahalo-dl-4.0.0`, or two map entries) make the
   second `REFUSED: ambiguous target`, so apply never writes one file twice. A
   malformed path argument is a `REFUSED` message, not a stack trace.

   **Known limit: group atomicity.** The moves of one apply are not atomic as a
   group. A failed move is rolled back from the staged backups, but a process killed
   in the middle of an apply (no chance to roll back) can leave some targets
   replaced and others not, and a `.promote-staging-N` directory beside the plan.
   The next plan and apply warn when they find such a directory; re-plan, read the
   `+`/`-` against the current targets, and delete the directory by hand.

Promotion never commits; the written files are ordinary working-tree changes for
the operator to review in `git diff` and commit.

## Worked example

Input `example.policy` (as produced/condensed by `polpAudit`):

```
grant codebase "file:/opt/jgdms/lib-dl/mahalo-dl.jar" {
    permission java.lang.reflect.ReflectPermission "newProxyInPackage.org.apache.river.mahalo", "";
    permission net.jini.security.AccessPermission "*";
    permission java.lang.RuntimePermission "accessClassInPackage.com.sun.proxy", "";
    permission net.jini.security.GrantPermission "net.jini.security.AccessPermission \"*\"";
};
grant codebase "file:/opt/jgdms/lib/mahalo.jar" {
    permission java.security.AllPermission;
};
```

Run:

```
java ... org.apache.river.tool.ProxyPolicyGenerator example.policy
```

Generated `example.policy.grantperm` (the non-proxy `mahalo.jar` grant is
ignored; the meta `GrantPermission`/`AllPermission` are not absorbed):

```
// <Apache licence header>
//
// GrantPermission ceilings synthesised by ProxyPolicyGenerator from
//   example.policy
// ...
// proxy codebase: file:/opt/jgdms/lib-dl/mahalo-dl.jar
// proxy-shape permissions present: true
grant codebase "file:/opt/jgdms/lib-dl/mahalo-dl.jar" {
    permission net.jini.security.GrantPermission "java.lang.RuntimePermission \"accessClassInPackage.com.sun.proxy\"; java.lang.reflect.ReflectPermission \"newProxyInPackage.org.apache.river.mahalo\"; net.jini.security.AccessPermission \"*\";";
};
```

Generated `example.policy.proxy-permissions/mahalo-dl/META-INF/PERMISSIONS.LIST`:

```
# <Apache licence header>
# Declared-needs manifest for proxy codebase:
#   file:/opt/jgdms/lib-dl/mahalo-dl.jar
# Generated by ProxyPolicyGenerator (do not edit by hand).
# Source policy: example.policy
# Source policy SHA-256: <64 hex digits>
# Generator: ProxyPolicyGenerator <version>, list format 3
# Generated: <date>
# Entries: 3 live, 0 dropped, 0 held back
(java.lang.RuntimePermission "accessClassInPackage.com.sun.proxy")
(java.lang.reflect.ReflectPermission "newProxyInPackage.org.apache.river.mahalo")
(net.jini.security.AccessPermission "*")
```

The ceiling is scoped, by default, to the proxy codebase itself (per-codebase
granularity). Before deployment, **attach** each ceiling to the grant block of
the domain that actually calls `DynamicPolicy.grant` for the proxy (the service
/ exporter), re-scoping the `codebase`/`principal` clauses for that granting
role — the fragment's header comment says so.

## SOW open questions — decisions taken

1. **Canonical proxy-artefact naming.** Hard key = `*-dl.jar` / `httpmd:` /
   `digest` scope (matches the modules that ship `PERMISSIONS.LIST` today).
   Configurable via `--proxy-regex`.
2. **Audit-time vs post-process.** *Post-process* over the recorded
   least-privilege policy — testable, round-trips through the existing parser,
   and keeps `SecurityPolicyWriter` simple. Mirrors `PolicyCondenser`.
3. **Heuristic aggressiveness.** Name convention is the sole hard key;
   permission-set shape is corroboration/annotation only (opt-in `--strict`
   requires both).
4. **Ceiling granularity.** *Per proxy codebase*, scoped to that codebase by
   default, with a header note to re-attach to the granting role at deploy time.
