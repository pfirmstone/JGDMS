The DNS trust and URL replay problems are particularly fundamental flaws in the original model 
— they undermine the CodeSource as a security boundary at the most basic level.

If your policy grants are keyed on URL and you trust DNS to resolve that URL consistently, then 
DNS poisoning or CDN compromise lets an attacker serve different bytes at a trusted URL and those 
bytes inherit the grant. The DigestCodeSource / DigestGrant approach cuts that attack surface completely 
— the URL is just a locator, the SHA-256 of the actual bytes is the security-relevant identity. 
A URL change, CDN migration, or man-in-the-middle substitution at the same URL all produce a hash 
mismatch and the grant simply doesn't fire. The URL is essentially demoted from a trust anchor to a hint.

The URL replay attack is more subtle and gets less attention. The original model's CodeSource.implies() 
uses URL equality/prefix matching, which means a cached grant from a previous legitimate load of a 
URL can be replayed — present the same URL, get the same grant, even if the bytes have changed since 
the grant was originally issued. DigestCodeSource eliminates the replay window because the hash is 
computed at load time from the actual bytes on the wire, not from a cached URL lookup. The two-layer 
cache in SecureClassLoader (JarResponseCache + digestCache) reinforces this — once a (URI, algorithm) 
pair is resolved to a digest, it's pinned for the JVM session, preventing the same URL from serving 
different bytes on a re-request.

Circular references are precisely the feature that forces a serialization format to carry

exist (at least partially) before its fields are populated so that a later field can

with validation-before-construction: you can't run check(GetArg) before assignment if the 
object graph requires the object to already exist so something else can reference it.

So the @AtomicSerial subset and the DER format are aligned by construction. Both demand an 
acyclic object graph that can be decoded depth-first, each object fully validated and 
constructed before its parent. DER's SEQUENCE/SEQUENCE OF nesting expresses exactly a 
tree (or DAG without cycles) — there's no native back-reference mechanism in DER, which 
in any other context would be a limitation but here is exactly the property you want. 
The encoding can't express a cycle, the validation contract can't tolerate one, and the 
existing wire subset already doesn't produce one. Three layers in agreement.

The schema modules I drafted in §7 are already acyclic — SEQUENCE OF nesting with no

asn1
-- A collection-valued field, whatever its eventual concrete type:
CollectionField ::= SEQUENCE SIZE(0..MAX) OF Element

-- A map-valued field:
MapField ::= SEQUENCE SIZE(0..MAX) OF SEQUENCE {
    key     Element,
    value   Element
}
There is no MapSerializer/SetSerializer/ListSerializer wire type. There's just a bounded

the schema SIZE constraint, enforced before allocation by any conforming decoder — JVM or not.

the object copies out of it and discards it, exactly as it does with the Java carrier today.

The distinction is between intrinsic order and imposed order. My "values and bounds, never behaviour" 
rule was right for collections whose order is a property the receiving object decides 
— a SortedSet imposes its comparator's order regardless of wire order, a HashSet has no 
meaningful order at all. But an array is an ordered sequence by its very type 
— the order is part of the value, not a behaviour imposed afterward. 
principals[0] versus principals[1] is semantically distinct data, and for a SPIFFE principal chain 
or a certificate path, the order carries meaning: the leaf-to-root ordering of an X.509 chain, 
or the precedence order of principals in a Subject. Reorder it and you've corrupted the value, 
not just changed a presentation detail.

So the corrected principle is: the wire format preserves order when order is intrinsic to the 
value (arrays, sequences, chains), and does not assert order when order is an imposed behavioural 
contract (sorted/hashed collections). The good news is DER handles both correctly without any 
special mechanism, because SEQUENCE OF is defined as ordered. DER preserves element order in 
SEQUENCE OF by specification — it's BER/DER's encoding of an ordered list. So:

An array field → SEQUENCE OF Element, and the order on the wire is the order of the array, 
preserved by DER, and the receiving object keeps that order because the array type is ordered. 
No special handling — DER already does the right thing.
A SortedSet field → also SEQUENCE OF Element, but the receiving object imposes its comparator 
order during construction and ignores wire order. Also no special handling.
The subtlety is that both encode as SEQUENCE OF and both preserve wire order at the encoding layer 
— the difference is purely in whether the receiving check()/constructor relies on that order 
or overwrites it. For an array it relies on it; for a sorted collection it overwrites it. 
The wire format doesn't need to distinguish them because preserving order is harmless for 
the collection case (the order is simply ignored) and essential for the array case.

Where this needs care is the SPIFFE principal ordering specifically. If a UserSubject's 
principals or a DomainIdentityRecord's principals have a required order — leaf certificate 
principal first, or a specific precedence — then the SEQUENCE OF Principal in §7.1/§7.2 must 
be treated as order-significant, and both the encoder and the receiving check() must respect it. 
That's already what DER SEQUENCE OF gives you, so the schema is correct as drafted 
— but the standard must state explicitly that the order is significant for these types, 
so a non-JVM implementer doesn't treat the principal list as an unordered set and reorder it 
(e.g. by canonicalising or sorting for some other reason). An implementer who assumed 
"it's a set of principals, order doesn't matter" would break SPIFFE chain validation.

So the principle refines to a three-part statement for §3:

The wire format carries values and bounds. Where order is intrinsic to a value — arrays, 
principal chains, certificate paths, any sequence whose indices are semantically distinct 
— that order is preserved on the wire and is significant; encoders must not reorder and decoders 
must not canonicalise it away. Where order is an imposed behavioural contract — sorted or 
hashed collections — it is neither asserted nor relied upon on the wire; the constructed 
object imposes it after validation. Everything else behavioural (uniqueness, mutability, null-handling) 
belongs in the constructor, never the wire.

This means §7.1 and §7.2 need an explicit annotation on the SEQUENCE OF Principal fields: 
order-significant. And the conformance section §9 needs a clause: a conforming implementation 
preserves the order of order-significant sequences and must not reorder, deduplicate, or 
canonicalise them. That's the clause that protects SPIFFE chain ordering across a JVM/non-JVM boundary.

The linked-list point is the same case as arrays — a linked list is an ordered sequence, 
its order is intrinsic, so it encodes as an order-significant SEQUENCE OF exactly like an array. 
The receiving object reconstructs the linkage in wire order. No separate treatment needed.

For Float/Double I recommend encoding the raw IEEE-754 bits as an OCTET STRING rather than

round-trips deterministically everywhere, which matters for any signed object.

and guarantee exact round-trip. X500Principal is the free consistency win — it's already

That's a judgment call that depends on how your JERI framing actually lays bytes out.

signature-input cutover design, which is the one genuinely breaking change in the whole migration).
