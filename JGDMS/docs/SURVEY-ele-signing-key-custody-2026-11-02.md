# Survey: can i.MX95 ELE hold the SVID/TLS signing key (2026-11-02)
Method: "PDF text" = I ran pdftotext on the saved NXP PDF and read the text itself. "Summary" = WebFetch model summary of a page, not the page. "Search-only" = search snippet. "(mine)" = my inference. Nothing filled from memory. Extends SURVEY-som-hardware-root-of-trust-2026-11-02.md.

## Answer (3 lines)
PARTLY. ELE can generate an ECDSA P-256/P-384 key, keep it inside, and sign with it (RM00284 4.5, PDF text); no private-key export exists except a caller-set PLAINTEXT flag.
A root-level process on the application cores can still ask ELE to sign anything while it holds a session (mine; the manual documents no per-process control, only a user-defined key-store "nonce").
The Linux/JCA path to it is thin: NXP's PKCS#11 (libsmw_pkcs11) + pkcs11-provider cover ECDSA but i.MX95 is not named, and the OP-TEE alternative keeps keys in OP-TEE, not ELE.

## What the documents do not say
- No setting that forbids the PLAINTEXT sign/generate flags (1d). No statement on app-core compromise (3c).
- Whether the TLS-offload example keeps the private key in ELE: the SMW TLS guide "does not explicitly state" it (summary).
- Signer and chain of `hsm_dev_attest`; format (PSA/DICE/proprietary); who runs NXP's root; M33/M7 access to ELE; whether SMW/pkcs11 is validated on i.MX95 (guide names i.MX9x; user_guide lists imx93evk, not i.MX95). A forum snippet (search-only) says libsmw_pkcs11.so.5 ran on an i.MX95 FRDM board.
- Conflict to resolve: imx-secure-enclave says i.MX95 "Key Import API Not Supported" and "HMAC not supported"; RM00284 covers import. Keys generated on-board is the safe path (mine).
