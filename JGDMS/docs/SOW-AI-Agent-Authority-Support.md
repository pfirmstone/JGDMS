# Scope of Work — AI Agent Authority Support (the agent-authority layer)

*Draft SOW — 2026-06-15. Grounded in `agent-authority-code-review-2026-06-14.md` and STD-007 §2.5.*

## 1. Objective
Build the **agent-authority layer** that STD-007 §2.5 currently states only as intent: let an AI
agent participate as a first-class, least-privilege peer — a **baseline playpen**, **human-gated
checkpoint escalation**, and (the keystone) an **attenuating, leased user→agent delegation** that
lets an agent act *later* on a strict subset of a user's authority without the user live in scope.

## 2. Why now / context — what's confirmed vs missing
The review confirms the **primitives are present and structurally enforce** the model:
- Conjunctive multi-principal grants — `PrincipalGrant.implies(Principal[]):203-235` uses
  `containsAll` (all-present, never any-present); `DigestGrant` adds a hard `DigestCodeSource` gate.
- `GrantPermission` enforced as a ceiling on both grant paths; `polpAudit` generates the floor.
- **No widening across `callAs`** — `SubjectDomainCombiner.combine():241-249` is additive-only
  (same CodeSource/perms/ClassLoader, principals added; privileged/static domains pass through),
  so attenuation is structural.
- Per-proxy grants are **GC-scoped** (`ProtectionDomainGrant.isVoid():192-196`), giving one-shot
  escalation for free.
- Peer-scoped network already exists — `AuthenticationPermission` `peer` clause (by X500Principal
  from the SVID on the authenticated SSL/JERI path).

But the **layer itself is entirely unbuilt** (review §4.1, Q-A, Q-D): no agent identity, no
baseline-playpen template, no checkpoint construct, **no notify-user channel**, and — the keystone —
**no leased/attenuating user→agent delegation** (`JwtPrincipal` is an immutable name holder with no
narrowing; `isVoid()` has no lease driver). Today the only co-presence mechanism is the live one.

**Design property to preserve:** the conjunction deliberately spans **two injection paths** — the
SPIFFE/workload principal is *stamped into the ProtectionDomain at class-load* (ambient,
`SecureClassLoader.java:342-352`, `WorkerSubject`), while the user JWT principal is *scoped-injected
by `callAs`* (`AccessController.java:995-1015`, which **excludes `WorkerSubject`**, `Subject.java:562-565`).
This separation stops workload identity leaking into the user-scoped chain; the leased delegation
**must not** break it.

## 3. Proposed approach (phased)
**Phase 1 — Agent identity + baseline playpen.**
Define the agent principal/SVID. Baseline = a **principal-less** (agent-code + process-SPIFFE-scoped)
grant — peer-scoped egress (`AuthenticationPermission`), a read scope, a write area, and the
notify-user capability. Generated by the `polpAudit` floor / the GrantPermission policy tool
(`SOW-GrantPermission-PolicyTool.md`). A principal-less grant already matches regardless of scoped
user (`PrincipalGrant.implies:204`) — this *is* the playpen.

**Phase 2 — Checkpoint escalation + notify-user channel.**
Escalation = the same permission space **with `∧ JwtPrincipal`**; live `callAs` co-presence satisfies
it, one-shot via DynamicPolicy GC-scoping. Build: (a) the **notify-user channel** (the agent's
escalation-request mechanism — a baseline capability), and (b) a **trusted checkpoint** that surfaces
the *actual* `Permission` being approved (rendered by the policy layer, **not** the agent's prose).
The human's approval is itself bounded by the admin's `GrantPermission` ceiling.

**Phase 3 — Leased, attenuating user→agent delegation (the keystone, review Q-A).**
Let a user confer a bounded, time-limited, **attenuating** (⊆ user authority) delegation to the
agent SVID so the agent can act *later* without the user live in scope. Two candidate mechanisms to
evaluate:
- a **`principal`-scoped, lease-bound grant** to the agent SVID, voided on expiry via a **new
  `isVoid()` driver** — the unused `PermissionGrant` decorator seam (`…:170-196`) is the intended hook
  (review §4.2); or
- a **SPIRE-minted short-TTL JWT** carrying the user `sub` claim plus a narrowed-scope claim
  (a derived/attenuated `JwtPrincipal` — which does not exist today and would need minting/narrowing).
Must be monotone-attenuating and non-repudiable; expiry = the dead-man switch (stop renewing → agent
goes dark).

## 4. Deliverables
Agent identity model; baseline-playpen policy template; notify-user channel + trusted checkpoint;
the leased attenuating delegation primitive (lease-void `PermissionGrant`/derived JWT); and promotion
of STD-007 §2.5 intent into a **normative agent-authority standard**.

## 5. Acceptance criteria
- An agent runs in its playpen **without** user co-presence; escalation requires either live user
  co-presence **or** a valid lease.
- Lease expiry kills escalated authority (dead-man switch); no renewal path widens authority.
- **No widening** across the delegation chain (the `SubjectDomainCombiner` additive property and the
  two-path SPIFFE-vs-JWT separation, incl. `WorkerSubject` exclusion, are preserved).
- A checkpoint approves the *real* `Permission`, not agent-supplied text; human grants stay within the
  admin `GrantPermission` ceiling.

## 6. Dependencies
The confirmed primitives above; `SOW-GrantPermission-PolicyTool.md` (baseline/PERMISSIONS.LIST
generation); STD-006 (data) / STD-007 (code); SPIRE/SPIFFE issuance for any derived-JWT path.

## 7. Open questions
Lease-bound grant vs derived/narrowed JWT (or both)? Lease renewal/heartbeat mechanism and its
failure semantics? Trusted-surface design for the checkpoint? Revocation propagation across cached,
content-addressed proxies? Does a derived JWT require new SPIRE registration semantics?
