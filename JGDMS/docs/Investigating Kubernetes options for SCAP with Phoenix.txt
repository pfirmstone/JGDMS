Investigating Kubernetes options for SCAP with Phoenix

2m 50s
Yes, Kubernetes can perform Phoenix's functions for SCAP cloud deployments — and the existing Helm chart already does exactly that. Here is the full mapping:

What Phoenix does (classic on-premise)

Phoenix is an ActivationSystem daemon. Its core responsibilities are:

Phoenix function	Implementation
Spawn service processes on demand	Activation.java forks JVM child processes via Runtime.exec()
Group services into isolated JVM processes	ActivationGroupDesc → separate JVM with its own policy/classpath
Crash detection & restart	ActivationMonitor.inactiveGroup() → re-spawns the group JVM
Persistent activation registry	ReliableLog (write-ahead log on local disk)
Stable service identity across restarts	ActivationID backed by Phoenix's idTable/groupTable maps
Security isolation between groups	Per-group GroupPolicy → separate SecurityManager policy file per JVM
Kubernetes equivalents already used in the SCAP Helm chart

Phoenix function	Kubernetes replacement in SCAP
Spawn/restart processes	Deployment (or StatefulSet) with restartPolicy: Always; liveness probes trigger pod restart on hang
Activation groups (JVM isolation)	One pod per role (each pod is its own JVM), container-level isolation is stronger than process isolation
Crash recovery	Kubelet restart policy + livenessProbe/readinessProbe (already in every host template)
Persistent activation log	PersistentVolumeClaim on host1 (Reggie) and host3 (Verdict Registry)
Stable service identity / location	Kubernetes ClusterIP Service (stable DNS) + Jini Lookup Service (Reggie, host1) for Jini-layer discovery
Per-group security isolation	PodSecurityContext (non-root, read-only rootfs), SELinuxOptions on host2-BAE, NetworkPolicy default-deny with explicit allow rules
SPIFFE identity	SPIRE agent DaemonSet + SVID hostPath volume mount in every pod (replaces LoginContext / Kerberos used by Phoenix)
How to wire SCAP services for Kubernetes (the one required code change)

Phoenix requires services to use ActivatableServiceDescriptor (giving them an ActivationID constructor). In Kubernetes, where the pod is always running, you instead use NonActivatableServiceDescriptor. All five SCAP services need to be started with their (String[], LifeCycle) or the convenience (String[], LifeCycle, String, Class<?>) constructor — which AbstractJiniService already provides. No Phoenix dependency is needed.

What Kubernetes does NOT replace (and why it does not matter for SCAP)

Lazy / on-demand activation — Phoenix wakes a service only on the first remote call. Kubernetes keeps pods running. For SCAP's continuous pipeline this is fine; if scale-to-zero were needed, KEDA could be added per-Deployment.
Multi-service packing into one JVM — Phoenix activation groups can host multiple activatable objects in one JVM. In Kubernetes the equivalent model is one service per pod, which is actually preferable for independent scaling and the BAE's security isolation requirements (SELinux type enforcement).
ActivationID persistence across registry wipes — ActivationIDs are opaque to Jini clients; they are looked up via Reggie. Kubernetes Service DNS is equally stable, so nothing is lost.
Summary

The SCAP Helm chart (deploy/helm/jgdms-scap/) already replaces Phoenix entirely: it uses Kubernetes Deployments for lifecycle, liveness probes for crash recovery, PVCs for persistence, ClusterIP Services for stable addressing, NetworkPolicy for isolation, and SPIRE for identity. The only prerequisite is that each SCAP service is started as a non-activatable service (using NonActivatableServiceDescriptor / the AbstractJiniService non-activation constructor), which avoids any dependency on ActivationID or the java.rmi.activation API.

Is it possible to support lightweight Kubernetes, or is the environment too restrictive?


Assessing lightweight Kubernetes support options

3m 12s
Yes, JGDMS can run on lightweight Kubernetes (K3s, MicroK8s, K0s, Kind, etc.). The environment is not too restrictive, but it does require using the right deployment pattern for each JGDMS concern. Here is the full analysis:

What works, what needs adaptation, and what is already ruled out
✅ Service deployment — already has a Kubernetes-compatible path
phoenix-containers.md (already in the repo) documents this precisely. Phoenix is incompatible with any container orchestrator for three fundamental reasons (multi-process spawning, persistent local log, dual lifecycle management), but NonActivatableServiceDescriptor + ServiceStarter as PID 1 maps cleanly onto a Kubernetes Deployment:

One pod per service role.
PID 1 is the service JVM — liveness probes, SIGTERM, cgroups limits all work correctly.
No persistenceDirectory required.
State goes to an external store (database, Cassandra, Outrigger on a StatefulSet, etc.).
⚠️ Multicast discovery — needs explicit unicast fallback
Standard Kubernetes CNI plugins (Flannel, Calico, Cilium, the Flannel-derived K3s built-in) do not forward IPv6 multicast across pods. LookupDiscovery multicast announcements and requests will be silently dropped at the virtual network bridge.

The solution is already in JGDMS: use LookupLocatorDiscovery / ConstrainableLookupLocator with an explicit locator pointing at the Reggie pod's Kubernetes Service DNS name (reggie.jgdms.svc.cluster.local:4160). Clients configured this way never need multicast at all. Reggie itself can disable multicast listening entirely in its .config if desired.

On a single-node lightweight cluster (K3s on bare metal, MicroK8s in loopback mode) multicast may work within the node's pod CIDR because all packets stay on the host, but relying on this is fragile and defeats the portability goal.

✅ JERI TCP/TLS communication — works natively
JERI endpoints are plain TCP connections, optionally upgraded to TLS. Kubernetes Service objects give each JERI server a stable ClusterIP + DNS name. The only requirement is that the JERI ServerEndpoint binds to 0.0.0.0 (not 127.0.0.1), which is already the default behaviour.

✅ SPIFFE/SPIRE — already designed for Kubernetes
SPIRE has a native Kubernetes node attestor (k8s_sat) and a Kubernetes workload attestor. spiffe-admin-deployment.md already references Helm, kubernetes auth method, and K8s Secrets. The SPIRE agent runs as a DaemonSet; each JGDMS pod gets its SVID from the local agent via the disk SVIDStore, exactly as it does on bare metal.

⚠️ Codebase server — needs a stable K8s Service address
Reggie and JGDMS services publish a java.rmi.server.codebase URL so clients can download proxy JARs. In Kubernetes this must be a URL that resolves inside the cluster (ClusterIP Service + DNS) and, if external clients exist, also outside it (NodePort, LoadBalancer, or Ingress). The codebase HTTP server can be a sidecar container or a separate pod behind a Service.

⚠️ DirtyChai JDK — requires a custom base image
JGDMS requires DirtyChai (or Java ≤ 23) for its authorization model. Standard eclipse-temurin:24 or openjdk:24 images will not work. A custom Dockerfile base image that installs the DirtyChai distribution is needed. This is a packaging task, not a fundamental incompatibility.

Dockerfile
FROM ubuntu:24.04
RUN apt-get install -y ... && \
    curl -L https://.../dirtychai-jdk-<version>.tar.gz | tar -xz -C /opt/jdk
ENV JAVA_HOME=/opt/jdk/dirtychai-<version>
ENV PATH=$JAVA_HOME/bin:$PATH
✅ Security policy files — no change needed
JGDMS policy files are read from paths inside the container image or from a ConfigMap-mounted volume. This is standard K8s configuration management.

✅ ReliableLog (for stateful services) — use a PersistentVolume
Reggie PersistentRegistrarImpl, Outrigger, Mahalo, etc. use ReliableLog with a local directory. In Kubernetes this maps to a PersistentVolumeClaim on a StatefulSet. This is the standard Kubernetes pattern for any stateful workload.

Summary
Concern	Kubernetes compatible?	What to do
Phoenix activation	❌ No	Use NonActivatableServiceDescriptor (already documented)
Multicast discovery	⚠️ Unreliable	Use LookupLocatorDiscovery with K8s Service DNS names
JERI TCP/TLS	✅ Yes	Bind to 0.0.0.0; expose via K8s Service
SPIFFE/SPIRE	✅ Yes	SPIRE DaemonSet + k8s_sat attestor
Codebase server	✅ Yes	Expose as K8s Service (ClusterIP + optional Ingress)
DirtyChai JDK	⚠️ Custom image needed	Build a base image with DirtyChai
Stateful service persistence	✅ Yes	Mount PersistentVolumeClaim to log directory
Security policy	✅ Yes	ConfigMap volume or baked into image
The environment is not too restrictive. The only genuinely blocking issue is multicast, which already has a first-class JGDMS alternative (LookupLocatorDiscovery). Everything else is packaging and configuration work that fits naturally into standard Kubernetes patterns. Lightweight distributions (K3s, MicroK8s, K0s) are functionally identical to full Kubernetes for all of these concerns.

The one remaining gap
The dirty-chai-latest release tag on pfirmstone/DirtyChai must actually exist and have a jdk-linux-x64.tar.gz + jdk-linux-x64.tar.gz.sha256 asset attached. If DirtyChai hasn't published a binary release yet, the gh release download step in the Dockerfile will fail. That's an upstream publishing task, not a JGDMS packaging task.

In summary: from the JGDMS side, the base image work is complete — it's a matter of minutes to run docker build once DirtyChai publishes its binary tarball. No additional coding or Dockerfile writing is needed.

Implementing support for IPv6 addresses in codebase

3m 18s
That's a correct and important characterization of the architecture. Here's what the code confirms:

The mechanism:

CodebaseAccessor.getClassAnnotation() is a Remote interface method — every client call is a live JERI remote call to the running service. It is not embedded in any serialized bytes. When PreferredProxyCodebaseProvider needs to load the smart proxy, it calls bootstrapProxy.getClassAnnotation() (line 1193 of PreferredProxyCodebaseProvider.java) over the JERI connection, getting back whatever the service currently returns.

On the service side, AbstractJiniService.getClassAnnotation() has two paths:

If Codebase_Annotation is explicitly configured in JiniServiceParameters — returns that static string.
If not configured — falls back to CodebaseProvider.getClassAnnotation(ifaces[0]) which reads java.rmi.server.codebase from the JVM, evaluated at the time of the call.
What this means for dynamic IPv6 addresses:

The bootstrap proxy stub contains the service's JERI endpoint address — that's the only thing that needs to remain stable between when a client discovers the service and when it calls getClassAnnotation(). The codebase HTTP server URL is fetched fresh from the server on every proxy download. A service can legitimately advertise a literal IPv6 address (e.g., http://[2001:db8::cafe:1]:9080/my-dl.jar) for its codebase server, and if that address changes (e.g., the codebase server moves), the service just updates what getClassAnnotation() returns — the next client to request the smart proxy automatically uses the new URL.

One nuance worth noting:

codebaseAnnotation in AbstractJiniService is final, set at construction time. Dynamic updates therefore work via the java.rmi.server.codebase system property fallback (when no explicit Codebase_Annotation is configured), or by subclassing the JERI-layer logic. In practice for Kubernetes: a service pod restarts with the new IPv6 address already in its java.rmi.server.codebase system property (set in the container ENTRYPOINT), so there's no in-flight mutation needed.

Revised Kubernetes implication:

My earlier statement that "the codebase URL needs to be a URL that resolves inside the cluster" was overly conservative. The codebase HTTP server can use a literal IPv6 pod address rather than a Kubernetes Service DNS name — it just needs to be reachable at the moment a client downloads the smart proxy. This also means a sidecar codebase HTTP server running on the pod's own IPv6 address is a perfectly valid and perhaps simpler deployment pattern.

Utilizing Spiffe services from outside the Kubernetes cluster

2m 27s
Now I have a complete picture. Here is the analysis:

External clients and SPIFFE services in a Kubernetes cluster
Yes — external clients can fully participate, with the right topology
JGDMS's SPIFFE identity model is built on X.509-SVID certificates and TLS, not on Kubernetes networking internals. "Being SPIFFE-enabled" for a client means: having a SPIRE agent running on the same host, getting its own SVID, and being able to reach the service over TLS. None of this requires the client to be inside the cluster.

The three things an external client needs
1. Its own SPIRE agent (on the external host)
An external client needs a SPIRE agent running on its own machine, attested to the same SPIRE server that issues SVIDs to the in-cluster services. The SPIRE agent's server_address must point to the SPIRE server (or HA load balancer) at a reachable address from outside the cluster. That address needs to be publicly stable — a fixed IPv6 address, a fixed IPv4 address, a DNS name, whatever is appropriate for your network.

The SPIRE server Service in the existing deploy/k8s/spire/spire-server.yaml is a plain ClusterIP — it is only reachable from inside the cluster. For external clients, it needs to be changed to a NodePort, LoadBalancer, or a routable address behind an Ingress on port 8081. A fixed, globally routable IPv6 address assigned to a LoadBalancer service is the cleanest option if your cloud/ISP provides IPv6 LoadBalancer support.

2. A matching registration entry in the SPIRE server
The SPIRE server needs a registration entry for the external client workload, using a node attestor that makes sense for bare-metal or VM hosts (e.g. x509pop, tpm, join_token, or aws_iid/gcp_iit if cloud VMs). The k8s_psat attestor used by the in-cluster SPIRE agent will not work for external clients — they need a different NodeAttestor.

The existing register-entries.sh in deploy/k8s/spire/ would need entries like:

bash
# External client machine attested by x509pop or join_token
spire-server entry create \
  -spiffeID spiffe://jgdms.example.org/client/my-app \
  -parentID spiffe://jgdms.example.org/spire/agent/x509pop/<fingerprint> \
  -selector unix:uid:1001 \
  -ttl 3600
3. The SPIFFE trust bundle (bundle.pem)
The external client's SPIRE agent will receive the trust bundle from the SPIRE server automatically during attestation. If using the JVM truststore option (spiffe-admin-deployment.md, Option A), the bundle.pem must be imported. This is the same file written to /run/spire/bundle.pem by the agent.

The policy file URL question
ConcurrentPolicyFile policy locations (java.security.policy system property, or policy.url.N entries in java.security properties) are plain URL objects. They can be:

file:// local paths (most common — baked into the container image or mounted via ConfigMap)
http:// or https:// URLs pointing at a policy HTTP server
For an external client that needs to fetch its policy from the cluster, a stable, fixed address is indeed required. The RemotePolicyProvider / PolicyUpdateListener pattern is even better: the client connects to the in-cluster PolicyService (via JERI over TLS with SPIFFE auth), registers for push updates, and gets new PermissionGrant[] arrays pushed to it whenever policy changes. This is a live JERI connection, so the endpoint address needs to be reachable and stable from outside the cluster.

The cleanest approaches in order of preference:

Approach	What needs a fixed address
Policy file as static URL (e.g., HTTPS endpoint on a fixed IPv6 VIP)	The HTTPS policy server VIP
RemotePolicyService push updates	The PolicyService Kubernetes LoadBalancer service (stable IPv6 VIP)
Policy baked into the container/client image	Nothing — no network access needed at policy load time
Summary
Requirement	Solution
SPIRE agent for external client	Run SPIRE agent on external host; use x509pop/join_token attestor
SPIRE server reachability	Expose SPIRE server port 8081 via LoadBalancer or NodePort service; assign stable IPv6 address
Trust bundle delivery	Automatic via SPIRE agent attestation; also importable to JVM truststore
Policy file location	Static HTTPS URL (fixed IPv6 VIP) or RemotePolicyService JERI push (recommended — no polling)
Service discovery	Use LookupLocatorDiscovery with the Reggie LoadBalancer service IPv6 address (no multicast needed)
The fixed IPv6 address requirement is real, but narrow: only the SPIRE server (port 8081) and the lookup/policy services need stable external addresses. Everything else — JERI calls to service instances, codebase downloads — are addressed via the service proxy stub's embedded endpoint, which is obtained at discovery time and can change between invocations via getClassAnnotation() as described in the previous question.
