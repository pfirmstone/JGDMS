## Part B, promotion
Design: new `ListPromotion` (package-private) reuses the generator's `generatedLists`, `compare`/`EntryDiff` (extracted from `diff()`), `liveEntries`, `moduleKey` (artefact name minus `-version`), `validateList`, `sha256Hex`. CLI on `ProxyPolicyGenerator`: `--out DIR [--plan-file F] --promote-plan ROOT...` and `--promote-apply PLAN --approve a,b [--allow-removals]`. Plan default path `<out>/promote.plan`; refused if under a module root. Plan records SHA-256 of generated list and target (`NEW FILE` if absent), ADDED/REMOVED, DROPPED/HELD notes, and "checked-in comment not carried over" lines. Apply: pre-checks every approved artefact and writes none if any fails; uses temp file + rename; keeps the target's EOL style (majority; LF for new).

## Operator decisions
1. Default of `--fail-on-held`: off. `policy-update` never sets it, so held entries are only WARNING-logged; make it default for promotion, or leave?
2. The content hash means every re-audit is refused over the earlier lists until `-Dpolicy.update.proxy.clean=true` (now forwarded by build.xml). Accept, or key on hash only for lists from other hosts?
3. CI gating of promotion: nothing runs it automatically. Suggest CI runs plan only and fails on a non-empty plan whose artefacts are not approved; the apply stays manual.
4. The 28 unmappable artefacts mean the sanitised `${HOST}` codebases (`__reggie-dl.jar_`) cannot be promoted; the audit needs real codebase names or a mapping option.
5. Promote also refuses lists with no `# Source policy:` line, so the 14 committed older lists cannot be re-promoted as is (intended; say if not).
