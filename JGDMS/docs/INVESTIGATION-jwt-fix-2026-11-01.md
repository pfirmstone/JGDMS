## Changes
1. BasicInvocationDispatcher: verifier and cache are one immutable holder `JwtState` behind one volatile field; `setJwtVerifier` publishes a new holder (new empty cache). Chosen over a generation counter or a lock because the swap is a single write: a reader sees old verifier + old cache or new + new; an in-flight verification under the old verifier writes into the discarded old cache.
2. Fail closed: JWT presented and no verifier -> IOException "no JwtVerifier is installed; refusing" (the readUserSubjects refusal pattern; the caller catches Throwable and calls request.abort(), lines ~1046/1075). DEFAULT_JWT_VERIFIER removed. Empty token refused. A verifier that throws RuntimeException is a refusal. No-JWT calls unchanged (test: callWithNoJwtIsUnaffected...).
3. Cache: key = SHA-256 of the token (no 64 KiB strings or bearer tokens retained); TTL = min(exp, now+300 s); max 1024 entries, strict (puts under a lock); never cache a missing, unparseable or past exp. Wire length check now `len < 0 ||` (HEAD: 0xFFFFFFFF reached `new byte[negative]`, NegativeArraySizeException).

## Findings NOT fixed (decisions needed)
A. **Principals are not bound to the token.** readUserSubjects reads principals from the wire (BasicInvocationDispatcher ~2320-2345) and verifies the token separately; nothing compares the token's `sub` to those principals, and jwtCount=0 with principals is accepted outright. With a perfect verifier, any P that holds one valid token for user X can present principals for user Y. In the model where JWT is S's whole user authentication this is the bigger hole. Needs a design (derive principals from verified claims). JwtVerifier returns void, so it cannot yet hand claims back.
B. DefaultJwtVerifier.containsExactAudience (HEAD :198-204): aud arrays are comma-joined, so scalar aud "evil,svc-a" matches expected "svc-a". Matters only if an issuer mints attacker-chosen aud strings. Not tested, UNDETERMINED exploitability.
C. extractJwtExp (dispatcher) is a substring scan, not the verifier's parser; a claim value containing `"exp"` can mislead it. Now bounded by the 300 s cap.
D. Claims-only DefaultJwtVerifier messages echo unauthenticated iss/aud (log injection); in signature mode the claims are signed. ES256 has one positive test, no negative-path tests. JwtLoginModule (jgdms-security-jwt) and docs under docs/ that say "null disables verification" not read or updated. Parser leniency (duplicate keys, unterminated strings) left; harmless once signed.

## Decisions needed
1. Missing exp: I chose REJECT in DefaultJwtVerifier (RFC 7519 makes exp optional, but a non-expiring bearer credential for user authentication is unsound); dispatcher never caches a token lacking a future exp, so a custom verifier that accepts exp-less tokens is re-run each call.
2. Cache bounds: 1024 entries, 300 s cap (a revocation or key rotation is ignored for at most 5 minutes). Wire limit left at 65,536 bytes, 4 tokens per Subject, 16 Subjects (HEAD constants); lower it if 64 KiB is too generous.
3. Behaviour change: deployments that ran with no verifier and sent tokens, or relied on the old structure-only default, are now refused until they install a verifier. Keep claims-only DefaultJwtVerifier public, or remove it?
4. Whether to take on finding A now.
